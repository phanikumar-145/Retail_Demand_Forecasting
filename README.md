# Retail Demand Forecasting and Replenishment System

A beginner-friendly, end-to-end Machine Learning project that forecasts daily product demand for a
retail chain and turns those forecasts into concrete **reorder quantities** for each store and product.

Built with plain Python, Pandas, Scikit-learn and Streamlit — no cloud services, no databases, no
complex architecture, and no hidden magic.

> **Dataset note:** the bundled dataset is **synthetic** — it is generated by Python code
> (`src/data_preprocessing.py`) to look and behave like a real retail export. It is **not real
> business data**. The pipeline is written so that a real CSV with the same columns can simply be
> dropped into `data/raw/retail_sales.csv`.

## 1. Project Overview

Retail stores must answer one question every day: *how much of each product should I order today?*

Order too little and you lose sales (stock-outs). Order too much and money sits in the warehouse
(dead stock). This project answers that question with data:

1. It analyses two years of daily sales history.
2. It cleans the data (missing values, duplicates, invalid entries).
3. It explores patterns with charts (weekly rhythm, festive peaks, promotions, stock levels).
4. It builds time-based features (lags and rolling averages) **without data leakage**.
5. It trains and compares three regression models and selects the best one on a held-out future period.
6. It forecasts demand for the next 7 days for every store and product.
7. It converts those forecasts into **reorder quantities** using lead time and safety stock.
8. It presents everything in an interactive Streamlit dashboard.

---

## 2. Problem Statement

A retail chain with several stores and many products records daily sales, prices, promotions and
available stock. Today the ordering decision is based on gut feeling, which leads to:

- **Stock-outs** on fast-moving products (lost revenue, unhappy customers), and
- **Overstock** on slow-moving products (blocked capital, waste, especially for perishable goods).

**Goal:** predict how much of each product each store will sell in the coming days, and translate that
prediction into a recommended order quantity that covers expected demand plus a safety buffer minus
what is already in stock.

## 6. Dataset Description

**File:** `data/raw/retail_sales.csv`
**Source:** synthetic (generated by `create_synthetic_dataset()` in `src/data_preprocessing.py`)
**Size:** ~35,000 daily records — 4 stores × 12 products × 731 days (2023-01-01 → 2024-12-31)

| Column | Type | Description |
|---|---|---|
| `date` | date | Sales date (daily) |
| `store_id` | text | Store identifier (`S01` … `S04`) |
| `product_id` | text | Product identifier (`P001` … `P012`) |
| `product_category` | text | Beverages, Dairy, Household, Snacks |
| `sales_quantity` | int | Units sold that day |
| `unit_price` | float | Price per unit |
| `promotion` | int | 1 = promotion day, 0 = no promotion |
| `stock_available` | int | Units available in store that day |

**Realistic patterns deliberately built into the data** (so a model has something to learn):

- a weekly rhythm (weekends sell more),
- a yearly seasonality (festive peak Oct–Dec, dip in February),
- slow growth over two years,
- promotions that lift sales by roughly 25–70% depending on the product,
- stock limits that occasionally cap sales,
- random day-to-day noise.

**Messiness deliberately injected** (so cleaning has real work to do):

- ~1% missing values in quantity, price, stock and promotion,
- ~0.4% exact duplicate rows,
- ~0.3% negative sales (impossible → data-entry errors),
- 5 impossible dates (`31/02/2024`),
- shuffled row order (an export is rarely perfectly sorted).

### Cleaning rules applied

| Problem | Treatment | Why |
|---|---|---|
| Unparseable / impossible date | row dropped | a time series row without a valid date cannot be placed in time |
| Exact duplicate rows | dropped | duplicate records double-count demand |
| Duplicate (date, store, product) keys | first kept | one row per store-product-day |
| Missing `sales_quantity` | median of the same store+product | preserves that product's normal level |
| Missing `unit_price` | median of the same product | prices are stable per product |
| Missing `stock_available` | median of the same store+product, else 0 | conservative estimate |
| Missing `promotion` | 0 (no promotion) | do not invent promotions |
| Negative sales / stock / zero price | set to missing, then imputed | physically impossible values |
| Extreme outliers (> 10× product median) | capped | prevents a few bad rows from dominating the model |

## 8. Machine Learning Models

All models are trained on the **same features** and evaluated on the **same future test period**.

| # | Model | Role |
|---|---|---|
| 1 | **Linear Regression** | Baseline. Simple, fast, easy to explain. If a complex model cannot beat this, it is not worth deploying. |
| 2 | **Random Forest Regressor** | Captures non-linear patterns and interactions (e.g. "weekend *and* promotion"). Default settings: 200 trees. |
| 3 | **Tuned Random Forest** | Same algorithm with a small `GridSearchCV` (8 combinations × 3 time-series folds) over `n_estimators`, `max_depth` and `min_samples_leaf`. |

### Features used (12)

| Group | Features | Why it matters |
|---|---|---|
| Calendar | `year`, `month`, `day`, `day_of_week`, `is_weekend` | weekly and yearly seasonality |
| Known-in-advance | `promotion`, `unit_price` | price and promotion drive demand and are known before the day |
| Lag | `lag_1`, `lag_7`, `lag_30` | the strongest signal in retail: recent sales predict next sales |
| Rolling | `rolling_mean_7`, `rolling_mean_30` | smooths noise, shows the current demand level |

### How data leakage is prevented

1. Data is **sorted by store, product and date** before any shift/rolling operation.
2. Every lag and rolling feature uses `.shift(1)`, so the value for day *T* only uses data up to
   *T-1*. Without this, `rolling_mean_7` for day *T* would include day *T*'s own sales — the model
   would look perfect in training and fail in production.
3. The train/test split is **chronological** (first 80% of dates vs last 20%), never random.
4. Lag and rolling features are computed **per store and per product**, so one series never
   borrows another series' history.
5. `stock_available` is **not** used as a model feature: it is only known for the past and would
   leak information about how much could be sold.

### Model selection rule

The model with the **lowest test RMSE** is selected. In retail, large misses are the expensive ones:
a big under-forecast causes a stock-out (lost sales) and a big over-forecast causes dead stock.
RMSE punishes those large errors harder than MAE, so it matches the business cost better.

## 9. Evaluation Metrics

| Metric | Formula (conceptually) | Unit | Interpretation |
|---|---|---|---|
| **MAE** | mean of \|actual − predicted\| | units | "On average we are off by X units per store-product-day." Very easy to explain. |
| **RMSE** | square root of mean squared error | units | Same unit as sales, but large errors weigh more. Used for model selection. |
| **R²** | 1 − (SS_res / SS_tot) | 0–1 | Share of the variation in sales explained by the model. 1.0 = perfect, 0 = no better than predicting the average. |
| **MAPE** (category report only) | mean of \|error\| / actual × 100 | % | Scale-free view, useful to compare small and large categories fairly. |

Errors are additionally reported **per product category** in `outputs/category_errors.csv`.

## 10. Forecasting Methodology

**Goal:** forecast demand for the next 7 days (2025-01-01 → 2025-01-07) for all 48 store-product pairs.

### Step-by-step

1. Take the last real date in the dataset as the **forecast origin**.
2. Generate the next 7 future dates.
3. For each store-product series, build the features for day 1 from **real history only**:
   `lag_1` = yesterday's real sales, `lag_7` = sales 7 days ago, `rolling_mean_7` = mean of the last
   7 real days, and the calendar features from the future date.
4. Predict day 1, clip the result at 0 (demand cannot be negative).
5. **Feed that prediction back into the history** and use it to predict day 2. Repeat for days 3–7.
   This is called **recursive (multi-step) forecasting**, and it is the only way to produce lag-based
   forecasts several days ahead when the real future is unknown.
6. Save the results to `outputs/forecasts.csv`.

### Assumptions

- **No promotions** in the forecast window (the promo calendar is not part of the dataset).
- Unit price stays at the **last known price**.
- The model keeps the patterns learned from 2023–2024; no external events are modelled.

### Limitations of lag features for multi-day forecasting

| Limitation | Consequence |
|---|---|
| **Error accumulation** | Day 1's prediction becomes day 2's input. A mistake propagates and grows, so a 7-day forecast is far less reliable than a 1-day forecast. |
| **Smoothing / flat forecasts** | Because predictions are fed back in, forecasts tend to be smoother than reality and can miss sudden spikes. |
| **No shocks** | Festivals, strikes, weather events and new competitors are invisible to a model trained on history only. |
| **Unknown promo & stock** | Promotions are assumed zero, and stock constraints are ignored during prediction (they are handled in the replenishment step instead). |
| **Single-step horizon mismatch** | The model was trained to predict one day ahead; using it recursively stretches it beyond its training assumption. |

## 11. Replenishment Calculation

For every store-product, using the **latest available stock** and a **3-day lead time** (default
assumption, configurable in `src/config.py` or with `--lead-time`):

```
expected_demand   = sum of predicted demand for the next `lead_time` days
safety_stock      = 1.65 × std(daily demand, last 30 real days) × √(lead_time)
reorder_quantity  = max(0, expected_demand + safety_stock − current_stock)
```

**Why these numbers?**

- `1.65` is the z-score for roughly a **95% service level**: it covers normal day-to-day ups and downs
  without holding excessive buffer.
- `√(lead_time)` makes the safety buffer grow with the delivery period but slower than the period
  itself (risk pooling), which is standard inventory practice.
- The buffer is based on the product's **own recent variability** (last 30 days), not a global average.
- `max(0, …)` means we never recommend a negative order.

### Worked example (from the bundled run)

> Store **S01**, Product **P002** (Dairy), lead time 3 days
>
> - Current stock = **140** units
> - Expected demand during lead time = **254.00** units
> - Safety stock = 1.65 × σ × √3 = **52.88** units
> - Reorder = max(0, 254.00 + 52.88 − 140) = **167 units**

### Assumptions

- Lead time is a **3-day default** because the dataset contains no supplier information.
- Current stock = the **last recorded** `stock_available` for that store-product.
- No orders are already in transit, and there is no minimum order quantity.
- Quantities are rounded **up** to whole units.

## 15. Results of the Bundled Run

Test period: **2024-08-13 → 2024-12-31** (last 20% of dates, 6,768 rows). Training: 2023-01-31 →
2024-08-12 (26,875 rows).

| Model | MAE | RMSE | R² |
|---|---|---|---|
| **Tuned Random Forest (selected)** | **9.666** | **13.071** | **0.7724** |
| Random Forest | 9.862 | 13.307 | 0.7641 |
| Linear Regression (baseline) | 10.346 | 13.899 | 0.7427 |

**Interpretation:** on a typical store-product-day the tuned Random Forest is off by about
**9.7 units**, and it explains about **77%** of the day-to-day variation in sales. All three models
land in a similar range, which is expected: the lag features carry most of the signal, and the Random
Forest adds a modest but real improvement over the linear baseline.

Category-wise errors (selected model):

| Category | MAE | RMSE | MAPE | Test records |
|---|---|---|---|---|
| Beverages | 11.75 | 15.45 | 16.2% | 1,692 |
| Dairy | 11.73 | 15.62 | 16.5% | 1,692 |
| Snacks | 8.37 | 10.81 | 17.3% | 1,692 |
| Household | 6.81 | 9.15 | 17.1% | 1,692 |

**Why Beverages and Dairy have the highest errors:** they are the highest-volume categories, so an
absolute error of ~12 units is only about **16%** of their typical daily sales. Household has the
lowest absolute error simply because it sells fewer units — its *percentage* error is similar or
slightly worse. This is why the report shows MAE **and** MAPE side by side: absolute error scales with
volume, percentage error does not.

Forecast and replenishment summary: 336 forecast rows (48 store-products × 7 days), **19 of 48**
store-products flagged for restocking, **956 units** recommended in total.

*(These numbers come from the bundled synthetic dataset with `random_state = 42`; re-running gives the
same results. Real data will produce different, probably less tidy, numbers.)*

## 16. Limitations and Future Improvements

### Limitations (be honest about these in a review)

1. **Synthetic dataset** — the model learns from generated patterns, not real business behaviour.
2. **Recursive forecast error growth** — 7-day forecasts compound the day-1 error; the further ahead,
   the weaker the prediction.
3. **Flat / smoothed forecasts** — feeding predictions back in reduces variance, so spikes are missed.
4. **No promotions in the future** — the model assumes zero promotions during the forecast window.
5. **Fixed lead time (3 days)** — real lead times vary by supplier and product.
6. **No stock in the model** — `stock_available` is excluded from features (it is not known in advance),
   so the effect of stock-outs on recorded sales is not fully corrected.
7. **No external drivers** — holidays, weather, competitor pricing and marketing campaigns are absent.
8. **Store and product IDs are treated as implicit only** — they are handled through grouped lag
   features rather than as explicit model features.
9. **Single-step training horizon** — the model is trained on a 1-day-ahead task and used recursively.
10. **Accuracy ceiling** — R² ≈ 0.77 means roughly a quarter of the variation is unexplained.

### Future improvements

1. **Direct multi-horizon models** — train one model per horizon (t+1 … t+7) instead of recursing.
2. **Better features** — holiday flags, day-of-month, payday effects, price elasticity, promo calendar,
   stock-out flags (`sales == 0 and stock == 0`), product-level aggregation.
3. **Gradient boosting** — try `HistGradientBoostingRegressor` or LightGBM; usually stronger than a
   plain Random Forest on tabular data.
4. **Probabilistic forecasting** — predict quantiles (e.g. P90 demand) and use them directly as safety
   stock instead of the σ × z approximation.
5. **Per-category models** — Dairy/Beverages and Household have different dynamics; separate models or
   category-level features could help.
6. **Proper inventory simulation** — compare reorder policies (s, S), service levels and holding costs
   over a backtest instead of a single-point calculation.
7. **Automatic retraining schedule** — retrain weekly and track metric drift.
8. **Real data integration** — connect to a POS export and validate against real stock-out and
   wastage records.
